# dbcheck

Чекер лабораторных работ курса «Разработка баз данных». Подключается к вашей базе PostgreSQL и проверяет пункты чек-листа лабы. Для этого он читает системный каталог (таблицы, ключи, ограничения, представления, функции, триггеры, роли, индексы) и выполняет сценарии `demo/*.sql`. На каждый пункт выводится ✓ или ✗ с причиной.

## Установка

Нужен Python 3.10 или новее.

```bash
pipx install git+https://github.com/bozhedom/dbcheck@v1
dbcheck --version
```

Без pipx: `pip install --user git+https://github.com/bozhedom/dbcheck@v1`.

Обновление: `pipx reinstall dbcheck` или `pip install --user --force-reinstall git+https://github.com/bozhedom/dbcheck@v1`.

## Запуск

Из корня репозитория, когда база запущена (`docker compose up -d`):

```bash
dbcheck --lab 1                 # шесть пунктов лабы 1
dbcheck --lab 1 --stars         # плюс задания со звёздочками
dbcheck --lab 1 --fresh         # пересоздать базу с нуля и проверить её
dbcheck --lab 2 --only 6        # только пункт 6
dbcheck --lab 2 -v              # показывать выполнение сценариев
```

| Флаг | Что делает |
| --- | --- |
| `--lab N` | Номер лабы, 1-5 |
| `--stars` | Проверить задания со звёздочками |
| `--only K` | Проверить только пункт K |
| `--fresh` | Выполнить `docker compose down -v` и `up` перед проверкой: создаётся ли всё из `db/` |
| `--all` | Проверить лабы с 1 по N |
| `--ci` | Режим GitHub Actions: копирует `.env.example` в `.env` и включает `--fresh` |
| `--dsn URL` | Строка подключения вместо `.env`: `postgresql://user:pass@host:5432/db` |
| `--repo PATH` | Корень репозитория, если запуск не из него |
| `-v` | Показывать выполнение сценариев |

Код выхода: `0`, если нет ✗; `1`, если есть ✗; `2`, если база не отвечает.

Значки в выводе:

| Значок | Значение |
| --- | --- |
| ✓ | Пункт выполнен |
| ✗ | Пункт не выполнен, рядом причина |
| 👁 | Автоматическая часть пройдена, остальное проверяет преподаватель |
| ◐ | Задание со звёздочкой выполнено частично |
| ⚠ | Предупреждение, на баллы не влияет |

## Подключение

Параметры берутся из `.env` репозитория: `DB_PORT` (по умолчанию 5432), `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, хост `localhost`. Переменные окружения `PGHOST`, `PGPORT` и другие имеют приоритет, `--dsn` заменяет всё.

Для лабы 4 чекер также входит под ролями `app_reader` и `app_writer` с паролями `APP_READER_PASSWORD` и `APP_WRITER_PASSWORD` из того же `.env`.

## dbcheck.toml

```toml
[project]
main_table = "tickets"          # главная таблица; если не указана, берётся самая большая

[lab4]
writer_call = "SELECT buy_ticket(1, 42)"   # бизнес-операция, которую должен уметь app_writer
```

## dbcheck run: сценарий по шагам

```bash
dbcheck run demo/lab1.sql            # шаги, ответы базы, сверка с «-- expect:»
dbcheck run demo/lab2.sql --sql      # вместе с текстом запросов
dbcheck run demo/race.sql            # окна [A] и [B] в двух подключениях
dbcheck run demo/lab3.sql --keep     # не откатывать изменения
```

Файл без `BEGIN`/`COMMIT` выполняется в одной транзакции и в конце откатывается, база не меняется. Файл с `BEGIN`/`COMMIT` выполняется как в psql, команда за командой.

### Формат сценария

```sql
-- 3. Отрицательная цена билета: ошибка CHECK
-- expect: error check
INSERT INTO tickets (session_id, seat_id, price) VALUES (1, 1, -100);
```

| Ожидание | Значение |
| --- | --- |
| `ok` | Без ошибки (по умолчанию) |
| `rows`, `rows 6`, `rows >= 10` | Есть строки, ровно 6, не меньше 10. Для DML без `RETURNING`: число изменённых строк |
| `value 42`, `true`, `false` | Значение первой колонки первой строки |
| `same 1` | Результат совпадает с шагом 1 |
| `error`, `error unique`, `error 23505`, `error "текст"` | Любая ошибка, ошибка вида (`unique`, `check`, `fk`, `notnull`, `raise`, `permission`, `deadlock`, `serialization`), код SQLSTATE, фраза в тексте ошибки |
| `plan seq`, `plan index`, `plan only`, `plan bitmap`, `plan <имя индекса>` | Что есть в выводе `EXPLAIN` |
| `blocked` | Шаг ждал блокировку (только в сценариях с окнами) |

Метки окон для гонок: `-- [setup]`, `-- [A]`, `-- [B]`, `-- [check]` (один boolean: `true`, если правило соблюдено), `-- [cleanup]`. Шаг, который не завершился за 2 секунды, считается ждущим блокировку: чекер переходит к следующему и выводит результат, когда блокировка снимется. Подробнее: `docs/scenarios.md` в шаблоне репозитория.
